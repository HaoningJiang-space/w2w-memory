# 先验证构造，再继续实验：独立复核结果

结论：**局部小环 → 固定字节比例 → 全局精确覆盖**这条构造，在当前 reticle-level
模型的明确条件下通过了独立验证。验证通过后才运行新种子的性能实验；没有通过
迁移数据、增加物理边、放宽满载服务或忽略 HB 容量获得收益。

本轮是根据用户给出的文字方法独立实现。所引用外部 ZIP 未在可访问的工作区和
Downloads 中找到，因此不声称审计了那份源码，也不把其结果当作本轮运行结果。
代码仍只有 `main` 分支，旧实验语义不变。

## 1. 首先验证第一性原理

采用固定、非负字节矩阵 A，严格保持：

\[
\sum_m A_{cm}=1,\qquad \sum_c A_{cm}=1,\qquad f_{cm}=A_{cm}r_c.
\]

每个对象采用同一固定条带比例，无复制、无按活动集合重新驻留、无 memory 转发。
当前每 C 有 4 GiB 数据，列和为 1 使每 M 驻留 4 GiB，低于原有 16 GiB 容量。
HB 路径由实际区域 overlap 得出；端口配置和 memory/controller 容量不变。

将资源约束写成 Lr≤q，令 h 是当前活动节点的单位保底，r=h+x，则检查：

\[
Lx\le q-Lh.
\]

验证程序从 A 与 r 重新构造 memory、每条 HB、两端 port 的负载，不使用小环的
收益公式来验证它自己。对 memory 还核对：

\[
1-A^Th=A^T(1-h).
\]

这确认 idle 节点释放的是其原本占用的资源份额，而不是可任意替换的“总空闲带宽”。
通道唯一时 L 可直接构造；存在多路径时应保留显式 flow，不能随意固定一个 L。

## 2. 为什么该局部构造可行

一个简单交替环由两套局部匹配组成，分别承载 λ 与 1−λ；每个 C 的行和为 1，
每个 M 收到互补的两份权重，列和也为 1。不同组件可使用不同 λ。

设节点 i 两条独占路径上限为 a_i、b_i。当前端口不被多条 C–M 边共享，且边容量
小于 1。满载可行区间是 [max_i(1−b_i), min_i a_i]，因此两条比例均严格为正。
实际服务还必须通过端口、controller 和存储容量检查。

若某个必经 memory 的另一个数据使用者也 active，正比例与双方保底 1 会耗尽
该 memory，迫使该节点只能服务 1；否则可到独占上限。
这才允许使用“所有不同竞争者同时 idle”的解析速率式。

全局模型同时覆盖 C 和 M，各节点恰好进入一个组件。各组件的 memory、compute
以及所属端口因此互不重叠。在这个模型里，局部额外吞吐可相加，全局选择才可以
写成 0–1 集合划分。只覆盖 compute、不排除 memory 重复使用，会违反资源守恒。

故意构造七类错误，均被拒绝：字节重复、列驻留失衡、使用不存在的 HB、超额使用
HB、共享端口仍套独立路径公式、保底改为 0 仍套原公式，以及组件重复覆盖节点。

完整证书见 `artifacts/results/cycles/cycle_construction_certificate.json`。性能 runner 会拒绝 smoke 证书、
脏工作树证书、不同提交的证书以及不完整的配置验证。

## 4. 验证通过后运行的独立实验

两种 pitch、四类需求、三个目录上限，共 24 个设计。
**K 表示每个组件最多包含几个 compute，不是 bank fan-out。** 所有设计仍是每 C
两条正字节路径，冻结布局共 72 条使用边，底层物理图仍有 146 条 C–M 边。

- 新训练 seeds：110000–111023，共 1,024 个。
- 新测试 seeds：210000–214095，共 4,096 个。
- 每种需求分布单独离线设计；不声称一个布局同时达到四种分布的最好结果。
- 每个布局在测试前冻结，数组只读，测试前后 SHA256 一致。
- 24×4,096＝**98,304 个测试状态**全部重建资源负载并检查 Lx≤q−Lh。
- 另做 **816 次全局服务 LP**，包含预先选定测试状态与满载，分别检查吞吐和公共服务。
- 全局 LP 最大速率差为 8.53×10⁻¹⁴；24 个集合划分问题均报告 gap=0。

## 5. 保底与收益的边界也必须验证

所有测试中活动 C 保持注册的单位服务；满载公共速率为 1。但 **保底 1 不等于每个
场景都优于 pair 基线**。

pitch=25.6、K≤4 相对 pair：

- 集中需求中，10.38% 的测试集合平均吞吐下降，最大下降约 0.066667 TB/s/active C。
- 相关需求中，16.02% 的测试集合平均吞吐下降，最大下降约 0.200000 TB/s/active C。

优化的是训练分布下的期望吞吐，允许上述变化；没有把平均收益包装成逐场景支配。

| 分布，pitch=25.6 | pair 平均公共速率 | K≤4 平均公共速率 |
|---|---:|---:|
| 随机 9/36 | 1.157324 | 1.157324 |
| 随机 18/36 | 1.000000 | 1.000000 |
| 集中 9/36 | 1.000000 | 1.000000 |
| 空间相关 9/36 | 1.006885 | 1.018164 |

集中需求仍没有公共完成改善；相关需求的公共服务变化也不能直接当作完整应用
加速。K≤3 的相关需求平均公共速率甚至略降，进一步说明吞吐目标不等价于同步目标。

## 6. 目前可以确认什么

可以确认：在当前固定字节、单位保底、独立端口、reticle 内 pooled access 的
功能模型中，局部构造、容量比例优化和全局覆盖遵守资源守恒；相关需求收益来自
改变竞争者的组合，而非增加连接或免费移动数据。

尚未确认：重复 bank/LIO 模板能否提供这些字节路径、有限整数条带能否兑现连续
比例、实际汇聚器/连线/控制成本，以及 pad/DRAM 工艺可实现性。现有验证是功能与
区域几何证书，不是 bank 电路或芯片物理实现证书。

下一次扩展应保持这份资源证书作为参照，把 bank/template 或其他真实约束加入后
重新验证，而不是默认为小环构造已经完成硬件实现。本轮到此停止增加机制。
