# 完整返回路径的服务配置：从目标反求位宽、驻留与状态容量

2026-10-08；H/plus、36C+36M、32 banks/M。研究接续
[上一轮比例推导](SERVICE_PROVISIONING_REPORT.md)和
[架构形式化](../methods/SERVICE_PROVISIONING_ASSESSMENT.md)。
本轮没有修改 RTL、增加跨 bank engine pool 或改变 placement。

**新的设计结论是：服务配置必须联合选择位宽、驻留比例、在途请求容量和接收容量。**
相同几何上，增加 Shared 位宽并不保证更高的可用服务。固定 RX2 时，192-bit 的新比例
配置甚至略慢于160-bit；在数据与发送接口不变的对照中，RX3使较宽接口开始兑现收益。
因此 service graph 应表达共享状态约束下的可执行服务集合，而不只是独立边的带宽。

## 1. 为什么上一轮容量比例还不够

先前用 Home256、Shared 独占发送能力 s，以及每字最短请求生命周期推导：

\[
\gamma\le\min\left(2,1/\lambda,s/(1-\lambda),
 \frac{N/B}{\lambda\ell_H+(1-\lambda)\ell_S}\right).
\]

它正确保留了必要字节和请求容量，但其中的 s 来自发送端周期执行；接收路径有自己的
有限状态容量。当前回放在一个字开始传输时预留 RX entry，直到最后一拍经过链路并交付
后释放。部分字和在途完整字都会占位。

连续满宽打包时，256-bit 字在 W-bit 拍中的起点相位为 k·256 mod W。
设链路延迟 L，则第 k 个字的 RX 占位时间为：

\[
\tau_k=\left\lceil\frac{256+(k256\bmod W)}W\right\rceil+L.
\]

对完整相位周期取平均，满宽传输所需平均 RX 占位为：

\[
\boxed{\overline Q_{RX}=\frac W{256}\overline\tau
 =1+\frac{(L+1)W-\gcd(256,W)}{256}}.
\]

平均占位给出必要容量；可执行速率另由有限状态周期证书验证。
L=1 时160-bit虽然能在空拍起点用两拍发送一个字，但连续打包的字跨拍数为
2、3、2、3、2，不能把所有字都当成两拍。

| Shared W | 满宽平均 RX 占位 | RX2 实际字率 | RX3 实际字率 |
|---:|---:|---:|---:|
| 128 | 3/2 | 1/2 | 1/2 |
| 160 | 17/8 | 3/5 | 5/8 |
| 192 | 9/4 | 2/3 | 3/4 |
| 224 | 21/8 | 2/3 | 7/8 |
| 256 | 2 | 1 | 1 |

这里是单条 always-ready 路径，每槽最多一个原生字，有限 TX/RX 和固定链路延迟。
周期首尾状态重复、逐槽完整字/bit守恒；160/192-bit两种RX容量还用独立完整请求回放
核对了2400个纯远端读字。它不是全 wafer 的吞吐预测。

对既有 B 的 λ=8/13，RX2把 Shared 服务界收紧到
(3/5)/(5/13)=39/25=1.56；新 C 的 λ=4/7则被限制在
(2/3)/(3/7)=14/9≈1.556。**只增加位宽再按源端容量分数据，反而让必需远端字节
的瓶颈略微恶化。** 这预测了实际对照的排序，不需要拟合任务时间。

## 2. 从性能目标反求配置

选择宽 k3的稳态参考界 γF=min(2,N/96)，把其相对原生1的增量保留3/4作为明确目标：

\[
\gamma_t=1+\tfrac34(\gamma_F-1),\qquad \lambda_t=1/\gamma_t.
\]

在既有注册目录中固定 Home256，按完整字能力、请求生命周期及原生容量排除不可能项，
选择最小 Shared 位宽，再选择最小深度。保留所有接受/排除证书，不使用测试 trace 调参。

| 目标 N | γt | λt | 仅发送端/最短生命周期筛选 | 加入完整返回路径 |
|---:|---:|---:|---|---|
| 128 | 5/4 | 4/5 | 128-bit，D1 | RX2仍允许该选择 |
| 160 | 3/2 | 2/3 | 128-bit，D1 | RX2仍允许该选择 |
| 192 | 7/4 | 4/7 | 192-bit，D2 | RX2需要256-bit；RX3允许192-bit |

这些是目标未被必要界排除的最小宽度，不是有限任务的保证，更不是全部成本维度的最优。
N192的 C 在最终回放前由前两项约束选出；RX诊断是看到未兑现结果后提出的配对实验，
两阶段分开归档。未来选择器应直接使用完整路径合同。

## 5. 成本：更少的线与更多的接收状态

每颗memory按完整重复模板计费。RX payload代理为制造的bank-port边数×RX深度×256；
只统计payload，不含tag、credit和控制逻辑。下表的TX＋RX也只是payload代理和，不是面积。

| 设计 | Lane bits | TX bits | RX payload bits | TX＋RX proxy bits | 接入wire bit-mm |
|---|---:|---:|---:|---:|---:|
| Home | 8,192 | 8,192 | 16,384 | 24,576 | 120,832.0 |
| k2 | 16,384 | 8,192 | 32,768 | 40,960 | 241,561.6 |
| 宽k3 | 24,576 | 8,192 | 49,152 | 57,344 | 474,163.2 |
| B/RX2 | 18,432 | 24,576 | 49,152 | 73,728 | 341,664.0 |
| C/RX2 | 20,480 | 24,576 | 49,152 | 73,728 | 385,830.4 |
| B/RX3 | 18,432 | 24,576 | 73,728 | 98,304 | 341,664.0 |
| C/RX3 | 20,480 | 24,576 | 73,728 | 98,304 | 385,830.4 |

C/RX3相对宽k3少16.67%的lane、少18.63%的接入wire，但TX＋RX payload代理多71.43%。
它给出线预算与存储预算之间的新选择，不能称整体硬件只剩一个小比例。
完整CSV还保留pipeline、控制、bank-port边；局部selector线长仍未知，不用零补缺项。
包含RX的多维前沿中，h0_b1只保留Home/k2，四个无共享收益窗口只保留Home；
C/RX3在另外四个窗口保留为非支配选择。前沿由多个独立资源坐标定义，没有虚构统一面积权重。

既有B的RTL/P&R属于另一份已实现合同；这里新增192-bit/RX3只完成模型执行，未把旧35.6%或修复后的30.33%面积节省移植过来。

## 6. 架构贡献应落在什么地方

三张图仍然有用，但可研究、可实现的设计对象应是
**固定物理图上的、由驻留与部署配置约束的完整路径服务合同**。
制造模板 H包括全部方向、各bank的服务状态、位宽、TX/RX；部署配置z和地址布局L冻结；
运行时请求通过这些资源，产生实际完成时间。

这给出一条已经可执行的设计流程：

1. 从目标任务服务或完成时间、请求预算求必要资源界。
2. 由完整字返回路径的周期执行求 s(W,D_TX,D_RX,L)，保留共享资源约束。
3. 选择合法静态比例和伙伴，使所有必需来源都能支持目标。
4. 根据整个部署的方向需求删除重复发送状态；完整物理方向、RX及接线照常计费。
5. 对同一冻结逻辑任务闭环回放，再按多成本前沿选择实现。

在本轮中，前两步把“选192-bit”变成“192-bit＋足够RX”；第三步把N128的比例改成4/5；
第四步使用已有bank-local configurable实现。收益与成本因此来自同一个design，而不是
把一个接口的面积百分比与另一个模型的带宽百分比拼接。

完整服务合同可以用共享资源矩阵作容量放松，但有限状态仍需要周期见证和任务回放。
两个方向的独立边容量不能表达它们共用一个FIFO；发送带宽也不能表达RX的占位相位。
这些限制能实际改变被选择的硬件，因而使 abstraction 有了设计意义。

制造模板和部署需求的差异仍是WoW的关键：不同实例需要不同HB方向，但冻结部署后
并非每bank都需同时保留两套Shared发送状态。当前是每bank一套Shared TX，
**32-bank reticle仍有32套**，并不是整颗reticle一套engine。
若进一步共用跨bank engines，至少还要满足
K·q_engine≥目标Shared字率，并计入聚合线与输入仲裁；这应由新的容量瓶颈驱动。

## 7. 下一项设计：把静态映射的目标从边际热度改成共同完成

本轮owner对照指出一个明确缺口：训练中减少平均负载，并不等于减少每批最后一个
必要读任务的完成时间。max_c E[D_c]与E[max_c D_c]不同，常一起出现的专家可能
仍被放在同一个compute或同一对共享资源上。

下一轮固定本轮硬件，先改一个映射目标。对每个训练cohort/step保留完整专家集合，
用资源工作量下界而非边际次数评分。设d_cw为窗口的总必需字，配对i、j的memory工作量为：

\[
V_{M_i,w}=\lambda d_{iw}+(1-\lambda)d_{jw},\qquad
V_{M_j,w}=\lambda d_{jw}+(1-\lambda)d_{iw}.
\]

再加入各Home/Shared路径和每compute请求占位的工作量，构造
T_LB(w)=max_ρ V_ρw/q_ρ。按Σ_w p_w T_LB(w)比较受容量限制的expert交换或伙伴交换，
只在训练侧选映射；保留modulo与边际LPT，冻结后用新的请求集回放。
这个目标是可计算的乐观评分，最终任务依赖和尾部仍由执行器决定。

伙伴的互补性也可以用同一窗口下有/无共享的完成界差来评分，而不直接使用相关系数或
min(idle,demand)。它必须同时包含字节来源、路径状态和critical resource；多个pair权重
不必可加，因此先做小规模交换即可，不需要新的全局优化框架。

这会把下一步贡献集中到一个具体问题：**同一份静态映射，怎样同时减少任务的必要资源
竞争和制造时的服务状态？** 本轮已完成完整路径配置和回放诊断；共同完成感知的映射
是下一项待实现设计，不写成已有结果。

对归档做完整审计，无需重新执行十亿字回放：

```sh
mkdir -p memory_results
OPENBLAS_NUM_THREADS=1 OMP_NUM_THREADS=1 python -m w2w audit_return_path \
  --source artifacts/results/workload/provisioning_holdout/inputs \
  --primary artifacts/results/workload/provisioning_holdout/primary \
  --extension artifacts/results/workload/provisioning_holdout/target \
  --diagnostic artifacts/results/workload/provisioning_holdout/receiver \
  --output memory_results/return_path_audit.json
```

重新执行时分别使用`run_provisioning_holdout`、`run_provisioning_target`、
`run_return_path_diagnostic`，`--source`指向上述冻结inputs，`--output`使用新的目录、
`--workers 12`。原始输入重编译需在保留原relative raw路径的hn072输入包运行
`audit_provisioning_holdout --verify-raw`；便携归档可验证提取与全部文件身份。
