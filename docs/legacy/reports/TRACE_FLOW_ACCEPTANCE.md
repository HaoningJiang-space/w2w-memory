## 复查中实际补上的缺口

此前审计通过重新计算 `window_certificate` 和 `check_bound`，已经将 trace、设计和
驻留的身份绑定到回放；并非只信任两个文件里相同的字符串。
但交付核对主要检查总量，无法充分独立排除“总字数正确、具体资源分配错误”。

新增 `validation.patterns_replay.check_frozen_accounting`，从冻结驻留证书重建：

- 每任务的 bank 字节份额；每 bank 的 native words；每条 bank/port 路由的收发量。
- 任务 release、依赖、开始/读完成/最终完成时间的关系，同一 compute 不重叠。
- 总 makespan 与任务完成的一致性，以及嵌入的 design/residence 内容与哈希一致性。

新增反例让全局总量保持不变，只交换 bank 或 route 的交付计数；旧总量检查会接受，
新检查必须拒绝。另一个反例将子任务整体提前一槽、保持持续时间，验证依赖检查。
已有 48 组结果通过这些更强检查；补的是验收覆盖，没有修改历史性能数字。

## 仍然需要明确保留的限制

1. **它是模型执行，不是 GPU 推理。** 观测来自真实 expert routing；权重流量、冷读和
   serving cohort 由 execution spec 决定，不是采集得到的 DRAM transaction trace。
2. **归档审计不等于再次运行全部时隙。** 它独立核对可从冻结输入重建的身份、资源量和
   时间关系；逐槽守恒由执行器在原回放时检查。交付摘要不构成真实权重 payload 或 RTL 等价证明。
3. **统计范围有限。** 三组不同层/步的窗口用于诊断，不足以支持全 workload 总体收益，
   也没有新的架构全局最优性或端到端 LLM speedup 结论。
4. **工程能力有边界。** Python 下载器只恢复已经完整校验的文件；部分文件 Range 恢复、
   新数据集授权和任意规模自动重跑不属于此次完成项。没有凭据时不会自动绕过授权。
5. **物理验证独立。** 已有单 slice RTL/ASIC 证据保留原范围；当前 CPU flow 不包含整片
   DRAM/HB 的 PPA、时序签核或实际 DRAM command timing。

因此，当前可交接的是**有来源、有固定执行语义、有回放和独立审计的 CPU 研究流程**。
后续研究仍应验证服务收益与成本，而不能把流程验收通过写成架构已被全面证明。
