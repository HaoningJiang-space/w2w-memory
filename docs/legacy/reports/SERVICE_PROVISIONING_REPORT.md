# 从请求容量与完整字延迟共同设计静态驻留和服务接口

2026-10-08；实验源码 `eefe539d529cba64401b0cc66f7d4d06cbe40b71`；eex005。
[固定研究协议](../methods/SERVICE_PROVISIONING_STUDY.md)。

**本轮得到了一个实际设计改进：有限在途请求容量会改变合适的数据比例，也会改变值得制造的
Shared 位宽。** 原比例只匹配出口的独占能力；加入字从发起到交付的生命周期后，N128 时
A、B 都应优先考虑 Home=4/5。相同任务的分散读完成分别从79、77降到73槽；长尾任务
从319、310降到292槽。较窄的 A 与较宽的 B 在该配置下得到相同完成时间。

这使 service provisioning 有了具体的设计内容：同时选择静态驻留、完整字路径能力和
请求容量，再依据完整驻留删除多余的方向状态。新结果来自189次合成任务回放；既有48次
真实 routing 回放只重算完成下界。另一开发者的 RTL、真实输入流程和原始结果保持独立。

## 1. 从一个有限资源约束推导新布局

一个请求从发起到交付一直占用 outstanding entry。若每 compute 有 B 个本地 bank、
每 bank 原生能力为1 word/slot，Home 比例为 λ，整个流的速率为 Bγ，则至少需要：

\[
N\ge B\gamma[\lambda\ell_H+(1-\lambda)\ell_S].
\]

这里是占位时间的守恒：服务率乘每字最短占位时间不能超过请求容量。与 Home、Shared
及两颗 memory 的容量一起，得到：

\[
\gamma\le\min\left(2,\frac1\lambda,\frac{s}{1-\lambda},
\frac{N/B}{\lambda\ell_H+(1-\lambda)\ell_S}\right).
\]

本轮 B=32，request/native/link 延迟为1/0/1槽，256-bit Home 字的最短生命周期为3槽，
128/160-bit Shared 字为4槽。s 使用已通过完整字执行的 A=1/2、B=5/8。
N 是每 compute 的请求字数容量，不是 endpoint FIFO 深度。

在 N≥BℓH、ℓS≥ℓH 时，Shared 与请求容量两项随 λ 不减，Home 项随 λ 减少。
求交点得到该稳态松弛的一个最优比例：

\[
\boxed{\lambda^*=\max\left(\frac1{1+s},
\frac{B\ell_S}{N+B(\ell_S-\ell_H)}\right)}.
\]

比例由接口和请求合同推导，不在 trace 上拟合。本轮只新增三个冻结配置：

| 配置 | Home/Shared，bits | 深度 H/S | N 的推导点 | 原比例 → 新比例 | 稳态率上界 γ |
|---|---|---|---:|---|---:|
| a_n128 | 256/128 | 1/1 | 128 | 2/3 → 4/5 | 5/4 |
| b_n128 | 256/160 | 1/2 | 128 | 8/13 → 4/5 | 5/4 |
| b_n160 | 256/160 | 1/2 | 160 | 8/13 → 2/3 | 3/2 |

固定 H/plus、36C+36M、18对伙伴、合法 HB 路径和原有 endpoint。新比例同时改变地址驻留
与由驻留生成的冻结发起配额；仲裁算法不变。有限条带、队列及竞争仍由执行器计算。

## 2. 进一步推导：为什么 N128 下128-bit已经足够，而64-bit未必够

Home 的必需流量满足 γλ≤1。将它代入请求容量式，消去 λ：

\[
\boxed{\gamma\le1+\frac{N/B-\ell_H}{\ell_S}}.
\]

该界适用于 N≥BℓH，仍需同时满足原生及 Shared 容量。它揭示了一个容易遗漏的区别：
**提高 Shared 的持续发送率，与缩短一个完整字占用请求状态的时间，是不同的改进。**

当前完整字接收合同下，ℓS≥2+ceil(256/W)，其中2来自请求和链路延迟。
N128、ℓH=3时，仅此约束就给出：

| Shared 位宽 W | 最短完整字生命周期 | 消去比例后的 γ 上界 |
|---|---:|---:|
| 64 | 6 | 7/6 |
| 96 | 5 | 6/5 |
| 128–224 | 4 | 5/4 |
| 256 | 3 | 4/3 |

这些是解析必要界，未新增64/96/192/224-bit回放。它们不假定任意位宽比都能成为可执行率。
在当前两拍字的范围内，若 Shared 已足以送出目标必需字节，继续加宽不会提高这个请求
容量上界。反过来，为了在 N128 支持 γ=5/4，Shared 完整字生命周期必须≤4槽，故位宽
至少128 bit。A恰好位于这一拍数边界；其完成性能由下一节的真实执行确认。

这提供了可用于设计的规则：先从目标服务和请求预算求允许的字生命周期，再选能满足
该生命周期与字节率的位宽/深度，最后求驻留比例。请求状态不再是接口设计完成后才补的参数。

## 4. 同一账本中的设计变化

下面按每 memory 的制造模板计数；保留所有物理方向，使用 bank 端 serializer。

| 配置 | Lane bits | TX存储proxy bits | 接入wire bit-mm | 配置序列控制proxy bits |
|---|---:|---:|---:|---:|
| 原 A | 16,384 | 16,384 | 297,497.6 | 352 |
| 新 A，4/5 | 16,384 | 16,384 | 297,497.6 | 576 |
| 原 B | 18,432 | 24,576 | 341,664.0 | 1,376 |
| 新 B，4/5 | 18,432 | 24,576 | 341,664.0 | 576 |
| 新 B，2/3 | 18,432 | 24,576 | 341,664.0 | 352 |

N128 下，新 A 与新 B 的七场景完成时间相同，A少11.11% lane、33.33% TX存储及12.93%
接入线；请求预算相同。相对原 B，新 A 在分散/长尾更快，其余五场景相同，也降低上述三项。
相对原 A，位宽与队列不变，但序列周期由3变5，控制proxy增加224 bit/M。

完整 CostModel 还保留 pipeline、selector、HB 和驱动计数。这里的TX存储是模型中的
完整字队列，不是修复后RTL的所有FF；请求entries尚无metadata面积校准。这些计数可以
进行逐维成本比较，不能与局部 ASIC 面积百分比拼成整片系统面积。

## 5. Service fabric 应按什么粒度配置

对完整冻结驻留计算每 bank 的必要方向集合 S(m,b)，包括当前trace没有访问的正字节。
若一个发送上下文在整个部署期间只能绑定一个方向，那么同一模板bank至少需要：

\[
K_b\ge\max_m|S(m,b)\setminus\{Home\}|.
\]

两个方向不同时活动，并不使永久单方向绑定能够服务两者。配置时冻结与运行时切换是
不同能力。覆盖证书还独立检查每颗 memory 的方向并集，以判断现有广播配置是否足够。

| 布局 | 每模板潜在Shared方向上下文 | 完整驻留所需上下文必要数 | 每memory广播一个Shared方向是否兼容 |
|---|---:|---:|---|
| Home | 0 | 0 | 是 |
| k2 | 32 | 32 | 否，各bank组方向不同 |
| k3原布局及三个新比例 | 64 | 32 | 是 |

这里计的是方向覆盖上下文。当前 buffered k3 实现由64套潜在Shared发送状态降为32套，
仍然每bank一套；宽direct使用共用完整字寄存器，不能将方向数直接当成其实际serializer数。
这给出了映射输出的明确内容：每bank支持哪些方向、每实例如何绑定、保留多少bank并行度。

若进一步研究跨bank pool，每个engine的能力必须固定。以160-bit/slot、可兑现5/8
word/slot的一套发送器为单位，固定B的8/13布局：

\[
E\ge\left\lceil\frac{R(1-8/13)}{5/8}\right\rceil.
\]

32 words/slot 的满载基线至少需20个engine，52 words/slot 独占目标至少需32个。
4个engine在固定比例下最多支撑6.5 words/slot；即使重新优化比例，归一化率的容量上界
也只有1+4(5/8)/32=69/64。绑定网络和输入搬运还需另计。

因此现阶段的直接设计路线是**保留bank并行度，合并部署后冗余的方向状态**。
跨bank池化可以是后续候选，但须先给出服务目标与节省的完整成本，不能从“方向少”直接
推到“整颗memory只需一两个engine”。普通独立边容量图也不足以表示共享engine和请求
窗口；service graph 必须同时携带公共资源约束及绑定配置。

## 6. 将真实任务的等待分解到必需资源

既有显式DAG没有给同一个compute上无显式依赖的读任务连边；执行器仍将它们串行执行。
本轮下界取三类必要值的最大值：显式DAG、所有任务累加的native-bank/egress资源切口、
每compute所有任务的最短读时间及计算时间之和（再加最早release）。它不使用观测到的
任务排序作为已知依赖。

48个既有真实回放中，20个与新下界相等，33个至多相差8槽。部分代表值：

| 窗口、配置 | N | 实际完成 | 原显式DAG界 | 新完成界 | 剩余差 |
|---|---:|---:|---:|---:|---:|
| g0_b1，Home | 192 | 36,878 | 18,439 | 36,878 | 0 |
| g0_b1，宽k3 | 192 | 18,442 | 9,221 | 18,442 | 0 |
| g0_b1，B | 128 | 31,678 | 15,601 | 31,202 | 476 |
| g0_b1，B | 192 | 23,642 | 11,348 | 22,696 | 946 |
| g0_b16，宽k3 | 192 | 64,538 | 9,221 | 64,533 | 5 |
| g1_b4，B | 192 | 36,878 | 11,348 | 36,874 | 4 |

这改变了下一步设计的定位：有些窗口已接近其固定数据与资源的必要时间，改仲裁的空间
很小；请求受限且peer可用的窗口才是新比例值得验证的对象。差值只是当前下界未解释的
时间，不等于某个调度机制必然能回收的收益。

本轮没有用真实窗口选择新比例，也没有回放新比例的真实读阶段。原48份完成时间全部
复用原始记录；新增的是从相同冻结输入重建的资源证书。

## 7. 对架构贡献和下一步的判断

三图分离适合作为描述语言。它的设计价值应落实为：从驻留推导必要方向状态，从完整字
生命周期推导请求供给，再反向决定有用位宽和驻留比例。本轮给出了后一个闭环的解析
构造与可执行实例，也证明较强Shared接口可能在某种请求预算下没有额外任务价值。

下一步最值得做的是**固定这些公式生成的候选，在独立routing请求上验证联合配置的成本
与完成时间**。保留Home/k2/宽k3强对照，并在相同N下比较旧比例与新比例；使用训练部分
做共同的静态owner负载均衡，随后冻结owner、伙伴和对象地址映射。用测试输入回答：
为相同读阶段目标，是增加请求entries、增加Shared位宽，还是调整静态比例更划算。
本轮没有为这一比较先设面积权重。

实际设计顺序可以保持很小：目标完成时间与请求预算 → 必要路径/状态界 → 有限候选
位宽与比例 → 完整任务回放 → 多资源前沿。现有 matching 用于选择伙伴，configurable
用于实现证书允许的状态合并；无需先增加一个跨bank交换网络。
